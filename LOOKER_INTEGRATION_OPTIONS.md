# Integration Options - v1.1.0

## Current Looker Studio path

The implemented path is Looker Studio scheduled PDF email > Gmail/Workspace routing mailbox > Google Apps Script > authenticated Node.js ingestion > Poppler PNG conversion > WhatsApp through Baileys.

This keeps report generation and report access in Looker Studio. The bot does not need users' Google passwords, cookies, browser profiles or report-login sessions. It receives the PDF already generated by the schedule and resolves the destination from a secret plus-address.

A route is created inside each authorized destination chat. Its label is independent of the Looker Studio report title. Put one alias per destination chat into the schedule; the same report can reach several chats. Separate Gmail message IDs are independent deliveries, so redundant aliases for the same chat may produce repeated copies.

Use the account's actual scheduling capabilities. Confirm frequency, recipient and sharing constraints with Google's [scheduled delivery documentation](https://docs.cloud.google.com/looker/docs/studio/schedule-automatic-report-delivery). This email bridge does not itself require a Pro-only integration, but account restrictions and organization policy can still affect scheduling.

## Optional full-Looker Action Hub

The service also retains authenticated Action Hub endpoints for full Looker, which is a different product from Looker Studio:

```text
POST /actions or POST /actions.json  Integration discovery
POST /looker/form                   Destination/caption form
POST /looker/execute                Receive a pushed PNG
```

This path uses `LOOKER_ACTION_TOKEN` with the Looker `Token token="..."` authorization format and `LOOKER_ALLOWED_CHAT_IDS` for approved destinations. In production, no approved destinations means execution is disabled. The accepted attachment format is base64 PNG. Looker Studio email delivery uses the separate `/studio/email/ingest` bearer-token endpoint instead.

The full-Looker path needs tenant administrator configuration and acceptance testing. Its presence in the repository is not proof that an organization's tenant can use or has enabled it.

## Future inbound email options

The present Gmail bridge polls every five minutes, has a configurable recent-thread scan limit, and depends on Apps Script quotas. Its 2,000-message ledger, cutover and retry classification support a controlled pilot.

For higher volume or lower latency, evaluate Gmail API notifications or a supported inbound-email service with verified recipients, authenticated payloads and durable retries. Such a migration must preserve stable message identity, route authorization and the existing delivery ledger. It requires separate infrastructure/account configuration; it is not installed by this release.

## WhatsApp transport choice

Baileys is the implemented transport and uses one QR-linked WhatsApp account. It supports the pilot's chat workflow but is unofficial and the pinned package is a release candidate. Protocol changes, account restrictions and relinking can affect delivery.

Evaluate the official WhatsApp Business Platform against the actual destination and messaging requirements before company rollout. Do not assume an API migration will preserve group-chat behavior or existing session semantics. Account onboarding, approved templates and supported destination rules must be checked during that design decision.

## Production deployment choice

The supplied Render configuration is a free-tier pilot. It limits concurrent ingestion and PDF resource usage, stores routing/delivery state in MongoDB, and exposes version/readiness checks. It does not provide an always-on guarantee or a durable job queue.

Production options include always-on compute, managed secret storage, database backup/restore, durable workers, centralized alerts and report-content scanning. These require operational decisions and are recorded as remaining work, not code defects silently claimed fixed.

## Excluded designs

Cookie imports, private-report login automation, password storage and browser screenshot scraping are not part of this implementation and should not be presented as fallbacks. The bot delivers rendered pages from the scheduled PDF; it does not refresh underlying report data or alter report filters by itself.
